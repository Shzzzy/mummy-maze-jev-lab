# 木乃伊迷宫本地网页版设计

- 日期：2026-09-21
- 状态：已确认，可进入实施计划
- 目标版本：本地网页 MVP

## 1. 项目目标

制作一款可在本地浏览器运行的原创 2D 回合制迷宫游戏，核心玩法参考“木乃伊迷宫”类游戏。游戏用于快速验证 Jev 的判断能力，需要提供：

1. 完整可玩的人工模式。
2. 由 Jev 托管行动的 AI 自动模式。
3. 右侧 Jev 判断卡与量化结果。
4. 6 个渐进关卡、胜负判定和自动进入下一关。
5. 不暴露 OmniLabs API Key。

## 2. 非目标

首版不包含 Windows 桌面打包、账号系统、排行榜、云存档、多人模式、音效、广告、付费系统或第三方素材。首版不复制 PopCap 的地图、美术、名称素材或其他受保护资源。

## 3. 技术方案

采用“原生 JavaScript + Canvas + 本地 Node 服务”：

- 浏览器端使用 ES Modules、Canvas 和原生 DOM。
- 本地 Node 服务使用 Express 提供静态文件与 Jev API 代理。
- API Key 只保存在被 Git 忽略的 `.env` 中。
- 前端只访问本地的 `POST /api/jev/decide`，不接触真实 API Key。
- 游戏引擎与渲染器分离，规则引擎保持纯逻辑、可独立测试。
- 依赖尽量少，使用现代 Chrome 或 Edge 本地运行。

## 4. 游戏模型

### 4.1 地图与单位

地图是二维方格，包含以下元素：

- 地板：所有单位可通行。
- 墙壁：所有单位不可通行。
- 出口：玩家到达即通关，怪物可经过或停留。
- 陷阱：玩家进入即失败，怪物经过时安全。
- 钥匙：任何单位进入时切换全部闸门状态。
- 闸门：打开时可通行，关闭时阻挡所有单位。
- 玩家：由键盘或 Jev 控制。
- 白色木乃伊：优先水平追击，每回合最多移动两步。
- 红色木乃伊：优先垂直追击，每回合最多移动两步。
- 蝎子：优先水平追击，每回合最多移动一步。

### 4.2 回合规则

- 只有玩家执行移动后，怪物才会行动。
- 玩家没有等待操作，每次按键只移动一格。
- 玩家回合顺序为：移动玩家、判断玩家碰撞与地块效果、依次结算全部怪物。
- 怪物结算顺序固定为白色木乃伊、红色木乃伊、蝎子；同类型按关卡内配置顺序结算。
- 玩家进入怪物所在格，或怪物进入玩家所在格，立即失败。
- 玩家进入陷阱立即失败。
- 玩家进入出口立即通关。
- 玩家不能进入墙、关闭的闸门或地图边界。

### 4.3 怪物移动规则

木乃伊的一回合包含两个连续移动步骤。每一步都根据玩家当前位置重新计算方向：

- 白色木乃伊优先选择能在水平方向缩短与玩家距离的相邻格。
- 水平方向不能靠近时，白色木乃伊选择能在垂直方向缩短距离的相邻格。
- 红色木乃伊优先垂直方向，垂直方向不能靠近时改为水平方向。
- 蝎子每回合只执行上述逻辑中的一步，并优先水平方向。
- 如果优先方向与备用方向都不可走，单位停止，并放弃本回合剩余移动步骤。
- 墙、关闭的闸门、地图边界和其他怪物会阻挡移动。
- 怪物不能相互重叠，因此多怪可以互相卡位。
- 怪物踩到钥匙仍会切换闸门，踩到陷阱不会死亡。

### 4.4 闸门与钥匙

- 所有闸门共享一个开关状态。
- 初始开关状态由关卡定义。
- 任意单位进入钥匙格时切换全部闸门。
- 同一回合内，如果多个单位先后踩到同一钥匙格，每次进入都会切换状态。

## 5. 关卡与进度

首版包含 6 个原创关卡，使用不同布局和小地图元素，难度逐步增加：

1. 白色木乃伊教学关，引入墙体和出口。
2. 红色木乃伊关，强调垂直追击特性。
3. 蝎子关，引入与玩家等速的追击单位。
4. 白木乃伊、红木乃伊与闸门关。
5. 陷阱、多钥匙与闸门组合关。
6. 多只木乃伊和蝎子组合关，要求利用互相卡位。

每个关卡都保存为独立数据定义，并通过预设操作序列回放测试验证可通关。玩家通关后显示简短本关汇总，随后自动进入下一关；第六关完成后显示六关总汇总和导出按钮。失败时游戏暂停，玩家可重试本关。重试会完整重置玩家、怪物、钥匙、闸门、回合和本关决策记录。

## 6. 界面与交互

页面采用三栏结构：

- 顶部：游戏标题、当前关卡、重开按钮、`AI 自动`按钮。
- 中央：正方形 Canvas 迷宫。
- 右侧：Jev 判断卡、当前指标、关卡汇总与本关历史。

迷宫使用代码绘制的原创古埃及石墙和地砖风格。玩家、怪物和闸门状态必须通过颜色和形状明确区分，不依赖第三方图片。

方向键控制玩家。`AI 自动`按钮开启或关闭 Jev 托管；托管开启时禁用键盘操作。玩家移动、怪物移动按“玩家 → 白木乃伊 → 红木乃伊 → 蝎子”的顺序播放约 180 毫秒的补间动画，避免同一回合内的动作无法辨认。

## 7. Jev 判断卡

每个 AI 回合只发起一次 System One 请求，同时包含两个问题。

### 7.1 问题一：是否应优先靠近出口

- 类型：`noul`
- 展示标题：`现在是否应该优先靠近出口？`
- 展示格式：`Yes` 为返回的 `noul` 概率，`No` 为 `1 - noul`。

### 7.2 问题二：最佳方向

- 类型：`choice`
- 展示标题：`最佳动作`
- 候选项：`up`、`down`、`left`、`right`
- 展示格式：显示四个方向的完整概率。
- 最终动作：采用 `choice` 返回值，并显示对应置信度。

右侧卡片示例：

```text
Jev：现在是否应该优先靠近出口？
Yes：18%    No：82%

最佳动作
上：4%    下：91%    左：3%    右：2%

最终执行：下（91%）
```

Jev 只能返回四个方向之一，不能返回等待。即使置信度低或与 Yes/No 判断看似矛盾，游戏仍严格执行 Jev 选择的方向，不进行本地安全兜底。

## 8. Jev 接口设计

请求链路：

```text
浏览器 -> POST /api/jev/decide -> Node 本地服务
Node 本地服务 -> POST /v1/systemone -> OmniLabs
```

Node 服务使用以下环境变量：

- `OMNILABS_API_KEY`：必填，值为本地测试 Key。
- `OMNILABS_BASE_URL`：可选，默认 `https://omnilabs.vibeadmin.cn`。

服务固定使用 `jev-latest`，请求体中的 `state` 包含：

- 当前关卡编号与地图尺寸。
- 完整静态地图，包含墙、陷阱、钥匙、出口和闸门。
- 玩家位置。
- 全部怪物类型、编号和位置。
- 全部闸门当前状态。
- 当前回合数和当前关卡目标。

System One 的 `questions` 包含：

- `toward_exit`：`noul`，判断本回合优先靠近出口是否最佳。
- `next_move`：`choice`，在四个方向中选择最有利于通关的动作。

服务返回给前端的字段包括：

- 最终方向。
- `toward_exit` 的 Yes 概率。
- 四个方向的概率分布。
- `next_move` 的置信度。
- 服务端实测响应耗时。
- System One 返回的输入与输出 token 数。
- 请求成功或可展示的错误信息。

API Key 不进入 HTML、CSS、JavaScript 包、浏览器存储或日志。

## 9. 数据流与状态机

1. 用户点击 `AI 自动`。
2. AI 控制器读取当前规则状态并生成快照。
3. 前端调用本地 `/api/jev/decide`。
4. 右侧显示“Jev 思考中”，阻止重复请求和键盘输入。
5. 服务返回方向与概率，右侧先记录判断。
6. 规则引擎执行 Jev 方向，并播放玩家及怪物动画。
7. 如果通关，记录本关结果，短暂展示汇总并自动进入下一关。
8. 如果失败，暂停并显示重试按钮。
9. 如果回合继续且 AI 仍开启，动画结束后自动发起下一回合请求。

同一时间最多存在一个 Jev 请求。AI 请求在途时不能再次点击 AI 按钮制造并发回合。

## 10. 指标与导出

右侧实时显示：

- 当前关卡和进行状态。
- 当前回合数。
- 本关用时。
- 最近一次 Jev 判断卡。
- 最近一次响应耗时。
- 最近一次输入与输出 token。
- 本关平均置信度、平均响应耗时和总 token。

本关历史记录每回合的方向、Yes/No 概率、四方向概率、最终方向、置信度、响应耗时、token 和行动结果。关卡完成后保留记录。

测试会话可一键导出 JSON，内容包括：

- 导出时间与使用模型。
- 每个关卡的结果、回合数、用时。
- 每个回合的完整 Jev 判断与响应指标。
- 失败原因或通关状态。

首版不持久化到服务器；刷新页面会清空会话。

## 11. 错误处理

- 请求超时：暂停 AI，显示“Jev 响应超时”和重试按钮。
- `401`：显示 API Key 无效，不继续自动操作。
- `422`：显示请求校验失败，并保留本地错误详情。
- `429`：提示请求过于频繁，允许用户手动重试。
- `5xx` 或网络失败：暂停并允许重试。
- 响应结构异常或方向不是 `up/down/left/right`：视为无效响应，不执行动作。
- 任何错误都不得触发本地 AI 或自动选择方向。

## 12. 测试策略

### 12.1 规则引擎测试

- 玩家每一步只移动一格，不能穿越墙、关闭闸门和边界。
- 玩家进入陷阱和与怪物碰撞时失败。
- 玩家进入出口时通关。
- 白色木乃伊的水平优先规则。
- 红色木乃伊的垂直优先规则。
- 蝎子的单步水平优先规则。
- 木乃伊被墙、闸门和怪物阻挡时放弃剩余步骤。
- 第二步重新计算玩家方向。
- 钥匙切换闸门，多个单位踩钥匙时连续切换。
- 怪物经过陷阱不死亡。
- 多怪不能重叠。

### 12.2 关卡测试

- 加载 6 个关卡时地图结构合法。
- 每个关卡至少存在一条预设通关序列。
- 回放预设序列后结果必须为通关。
- 重试后所有状态恢复为初始值。

### 12.3 服务测试

- 正常请求正确生成 System One 请求体。
- 正常响应正确提取 `noul` 与 `choice`。
- 超时、非 2xx、无效 JSON 和非法方向均返回明确错误。
- 响应和日志中不包含 API Key。

### 12.4 浏览器验收

- 六关可通过键盘正常游玩。
- AI 自动按钮能够连续控制取到通关。
- 右侧判断卡、概率、置信度、耗时和 token 正确显示。
- 动画顺序清晰且页面不卡顿。
- 失败重试、通关自动下一关和最终汇总工作正常。
- 导出的 JSON 能完整对应右侧记录。

## 13. 验收标准

满足以下条件即视为 MVP 完成：

1. 使用本地命令可启动网页服务并在浏览器打开。
2. 不设置 API Key 时游戏仍可手动玩，但 AI 模式显示明确配置提示。
3. 设置有效 API Key 后，Jev 可逐回合控制玩家。
4. Jev 每回合只能在四个方向中选择一个。
5. 游戏严格执行 Jev 的方向，不提供本地决策兜底。
6. 右侧完整显示并记录 Jev 判断和量化结果。
7. 6 个关卡均可通关并自动推进。
8. 自动化测试覆盖核心规则、关卡可解性和服务错误分支。
9. 仓库中不包含真实 API Key。
